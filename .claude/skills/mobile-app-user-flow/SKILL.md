# 모바일 앱 유저 플로우

첫 실행부터 사용자가 앱의 핵심 가치를 경험하는 순간까지 설계한다. 기존 앱을 검토할 때는 실제로 확인한 동선과 개선안을 구분한다. 구현 요청에서는 기존 화면과 라우팅, 데이터 저장 방식을 먼저 읽고 요청 범위 안에서 변경한다.

## 동선 설계

1. **첫 유용한 결과를 정한다.** 사용자가 이번 방문에서 무엇을 끝내거나 얻어야 하는지 한 문장으로 적는다. 설치 후 첫 실행, 재방문, 공유 링크 등 이번 작업에 해당하는 진입점을 확인한다. 핵심 흐름에서 이탈하거나 완료한 뒤 돌아갈 곳도 정한다.
2. **필요한 질문만 남긴다.** 답변이 어떤 화면, 추천 또는 기본값을 바꾸는지 연결한다. 필수 입력은 바로 다음 작업에 필요한 시점에 받고 이유를 보여 준다. 선택 질문은 명시적으로 건너뛸 수 있게 한다. 답을 건너뛴 경우에도 탐색 가능한 기본 경로를 제공하고, 저장되지 않은 답이나 맞춤화 결과를 화면에서 확정된 사실처럼 표시하지 않는다.
3. **핵심 행동을 미리 경험하게 한다.** 도움이 되는 경우 결과 예시, 짧은 체험, 샘플 데이터를 사용한다. 튜토리얼에는 무엇을 해 보는지와 예상 부담을 표시한다. 선택형 체험을 건너뛰어도 핵심 진입점에 도달할 수 있게 한다. 이미 익숙한 사용자에게 같은 안내를 반복하는지는 재방문 동선에서 결정한다.
4. **가입·권한·결제 시점을 정한다.** 로그인은 동기화, 거래, 보호된 데이터처럼 실제로 필요한 행동에 연결한다. 첫 단계에 인증이 필요한 서비스라면 이유와 다음에 열릴 화면을 알린다. 알림·위치·마이크 등 선택 권한은 관련 기능을 쓸 때 요청하고 거부하거나 미룰 때 이어갈 길을 둔다. 가입, 권한 허용, 구독, 결제는 각각의 결과가 버튼 문구에서 드러나게 한다.
5. **모든 주요 이동에 도착점과 복귀 경로를 적는다.** 화면별로 목적, 사용자가 누르는 동작, 진입 조건, 다음 화면, 뒤로 가기 또는 다시 열었을 때의 동작을 정의한다. 핵심 작업을 시작한 뒤 인증이 필요해지면, 가능한 경우 인증 후 원래 작업과 입력 상태로 돌아온다.

가입 없이 핵심 가치를 보여 줄 수 있는 쇼핑 앱은 상품 탐색과 상세 보기를 먼저 열고 주문 단계에서 필요한 정보만 받을 수 있다. 개인 계좌를 다루는 앱은 인증 전에는 샘플이나 기능 설명을 보여 주고, 실제 계좌 조회 시 인증을 요구할 수 있다. 화면 순서는 제품의 첫 유용한 결과와 접근 조건에 맞춘다.

## 전환 상태와 검증

- 로딩 중인 화면에는 무엇을 기다리는지 표시한다. 준비 완료 문구는 실제로 진행할 수 있는 상태와 맞춘다. 버튼이 비활성 상태라면 활성화 조건을 알린다. 실패하거나 응답이 오래 없으면 다시 시도하거나 나갈 경로를 제공한다.
- 실행 가능한 환경에서는 정상 경로와 제품에 해당하는 분기를 직접 확인한다. 예를 들어 질문 건너뛰기, 권한 거부, 뒤로 가기, 앱을 다시 열었을 때 재개 위치, 느린 응답이나 실패 후 재시도를 점검한다. 오류 후 중복 실행에 영향이 있는 제출이나 거래는 다시 눌렀을 때의 동작도 확인한다.
- 실제 앱 검토에서는 화면에 표시된 내용, 실행한 동작, 관찰한 도착점만 확인 사실로 기록한다. 버튼이 보인 경우와 이동이 성공한 경우를 구분한다. 실제 가입, 계정 변경, 권한 부여, 결제 또는 구독은 사용자가 허용한 범위에서만 실행한다.
- 결과에는 핵심 동선, 화면별 분기와 복귀 경로, 확인된 동작, 미확인 동작을 담는다. 설계안은 제안으로 표시하고, 미확인 흐름은 접근 조건이나 멈춘 화면을 함께 적는다.

## 참고 사례 · 플랭에서 관찰한 흐름

- 유입 경로 → 학습 목적 → 스피킹 수준 → 하루 학습량. 네 설문에서 답을 고르지 않고 `다음`으로 이동했다.
- 맞춤 학습 안내 → 습관 알림 제안 → `다음에 하기` → 학습 튜토리얼 소개. 소개 화면에는 워밍업, 기본기 트레이닝, 데일리 프리토킹과 예상 시간이 표시됐다.
- 튜토리얼을 건너뛰면 맞춤학습 준비 완료 및 회원가입 안내가 나타났다. 관찰 중 `다음`이 비활성 상태여서 회원가입 방식과 이후 홈, 학습, 결제 흐름은 확인하지 못했다. 이 사례는 온보딩과 분기 설계에만 참고한다.

## Claude Code에서 작업하는 방법

- **인자**: `/mobile-app-user-flow <요청>` 형태로 호출되면 인자를 이번 작업의 앱 종류와 목표로 사용한다. 인자가 없으면 대화 맥락에서 앱과 첫 유용한 결과를 추론하고, 추론이 불가능할 때만 짧게 묻는다.
- **설계 요청**: 코드가 없어도 된다. 결과는 채팅에 Markdown으로 정리하되, 화면 수가 많으면 흐름도(Mermaid `flowchart`)와 화면별 표(목적 · 동작 · 진입 조건 · 다음 화면 · 뒤로 가기/재실행 동작)를 함께 쓴다. 사용자가 파일이나 문서를 원하면 그에 맞춰 저장한다.
- **구현 요청**: 수정 전에 Glob/Grep/Read로 라우팅(예: React Navigation, Expo Router, Flutter `GoRouter`/`Navigator`, SwiftUI `NavigationStack`, Jetpack Navigation), 기존 화면 컴포넌트, 온보딩 완료·인증 상태를 저장하는 방식(AsyncStorage, SharedPreferences, UserDefaults, 서버 상태 등)을 먼저 확인한다. 요청 범위 밖의 화면이나 저장 구조는 바꾸지 않는다.
- **검증**: 실행 가능한 환경이면 앱을 실제로 띄워 아래 분기를 확인한다. 웹 빌드(Expo web, Flutter web 등)는 Playwright로 모바일 뷰포트에서 확인할 수 있다. 실행이 불가능하면 코드상 추론과 실제 확인을 구분해 보고한다.
- **기존 앱 검토**: 디자인 레퍼런스 도구(예: Mobbin MCP)나 브라우저 도구가 연결되어 있으면 사용할 수 있지만, 도구에서 본 화면도 "관찰한 사실"과 "추정"을 구분해 기록한다. 실제 가입, 계정 변경, 권한 부여, 결제·구독은 사용자의 명시적 허락 없이 실행하지 않는다.
